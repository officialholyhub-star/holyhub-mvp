## What was implemented

The existing `requireCrmUser` function now requires a verified Supabase MFA session for ALL CRM roles (including viewer) before performing a CRM staff database lookup. It reads Supabase Auth's `getAuthenticatorAssuranceLevel()` from the same server-managed `requireUser()` client and fails closed unless `currentLevel === 'aal2'` AND `nextLevel === 'aal2'`. Missing/no factors (`aal1/aal1`), unchallenged enrolled factor (`aal1/aal2`), apparent stale token after factor removal (`aal2/aal1`) and provider errors are rejected. The general HolyHub login remains untouched.

This implements **a requirement**, not a complete staff enrolment experience. Real staff accounts currently have **zero** Supabase subject bindings in the CRM database. The optional private CRM deployment is still dormant. No user can be promoted, provisioned or granted CRM access by this code alone. A secure MFA enrolment/challenge/recovery experience and a live server-side test are required before activation.

Reference: Supabase Auth AAL documentation https://supabase.com/docs/reference/javascript/auth-mfa-getauthenticatorassurancelevel and https://supabase.com/docs/guides/auth/auth-mfa.
